3 The Brain: Turbo Engine & AI Routing

The core intelligence engine resides in src/lib/turbo/. Rather than dispatching all requests to an expensive frontier model, the Turbo Engine performs automated heuristic complexity analysis:

Complexity Heuristics Algorithm

Incoming message threads pass through analyzeComplexity(messages):

  • Low Complexity: Triggered by greetings, simple translations, formatting requests, or message lengths under 100 characters. Automatically routed to llama-3.1-8b-instant on Groq.
  • Medium Complexity: Default conversational queries, standard summarization, and creative generation routed to llama-3.3-70b-versatile.
  • High Complexity: Triggered by keywords (research, architect, security, typescript, refactor) or context payloads exceeding 4,000 characters. Automatically escalated to OpenAI gpt-4o or Claude 3.5 Sonnet.

Sovereign & Local Inference Runtimes

For sensitive or air-gapped environments, ShadowTalk incorporates hardware-accelerated on-device execution:

  • WebGPU Engine: Probes GPU capabilities and VRAM via probeWebGPU(), deploying quantized Gemma models directly in the browser via Transformers.js and WebLLM.
  • Ollama Local Bridge: Detects local Ollama instances on port 11434 and streams tokens with zero external cloud requests.
  • BYOK (Bring Your Own Key): Enables users to provide OpenAI, Anthropic, or Groq keys stored strictly in encrypted client-side storage.

6 Security, Privacy & Stealth Architecture

Security is designed with zero-trust, client-side isolation principles:

End-to-End Encryption (E2EE)

Implemented in e2e-encryption.ts using standard Web Crypto primitives: PBKDF2 key derivation (100,000 iterations, SHA-256) and AES-256-GCM authenticated encryption with 12-byte initialization vectors. Passwords never touch any server.

Stealth Network Guard

Implemented in stealthNetworkGuard.ts. Monkey-patches window.fetch and XMLHttpRequest to actively reject any network requests outside a verified local whitelist (localhost, blob:, data:) when the stealth kill switch is engaged.

7 Backend & Data Pipeline

The backend employs a clever architecture that guarantees both high performance and cross-backend flexibility:

The Firebase PostgREST Query Adapter

The application communicates with persistence through src/integrations/local/client.ts. Behind this client, createFirebaseBackend() maps standard Supabase method chains (.from('table').select().eq().order().limit()) to native Firebase Firestore queries in firestore.ts. Complex operators that Firestore does not support server-side are automatically resolved through an in-memory fallback layer.

Cloud functions in functions/src/index.ts handle shared API rotation, rate-limit tracking across multiple LLM providers, and authorized token verification using Firebase Admin SDK.

10 Audit Findings & Actionable Recommendations

Based on our deep inspection, the following three actionable improvements are recommended:

1. Update Navigation & Footer Links Post-v3.0 Pivot

siteLinkAudit.test.ts flagged links in Footer.tsx and Navigation.tsx pointing to legacy pages (e.g. /marketplace, /ide, /computer) that were consolidated in v3.0.0. Updating these links to direct to active routes or adding lightweight redirect routes in App.tsx will restore 100% audit pass rates.

2. Add fake-indexeddb to Vitest Environment

adaptiveMemory.test.ts threw ReferenceError: indexedDB is not defined under happy-dom. In real browser environments, IndexedDB is native. Adding fake-indexeddb/auto to src/test/setup.ts will enable local memory unit tests to pass cleanly in headless CI/CD pipelines.

3. Code-Split Secondary Chatbot Modal Panels

The compiled ChatbotPage chunk is currently ~2.9 MB because heavy secondary modals (AdvancedSecurityAuditPanel, ModelFineTuning) are imported synchronously. Wrapping these auxiliary panels with lazy() will decrease initial load times on mobile connections.
